# signal-delivery

The desktop and configured-command worker for the pure [`signals`](../signals/README.md) checkpoint. Products supply an explicit D-Bus connection, or `None`, configuration, restored state, a batch policy callback and an injected clock. The library never opens the operator session bus itself.

`run` receives `NotificationRequest` values and returns `NotificationUpdate` values. Persist each state and its receipts before acknowledging `persisted`. The worker records unknown before sending; restored unknown attempts cannot automatically resend. A D-Bus appearance retries each eligible explicit failure once, under its original identity. Readiness is per route, so this never reruns a completed or unknown command.

Every actual Notify or command call requires current owner policy, including historical occurrences and grouped replacements. `PolicyCheck` asynchronously receives an owned `PolicyRequest { delivery_id, route, notices, attempt }`: the exact occurrence/route being admitted, all contributors to its summary and the process-local attempt lifetime. It returns a boxed, Send future yielding `Result<Authorization, PolicyFailure>` with one immutable decision per delivery. The worker naturally awaits all admission writes and asynchronous commit/rollback and guard release before receiving decisions; the callback uses no blocking runtime bridge. The worker completes non-effect D-Bus preflight and authorizes the batch immediately before Notify or command spawn. No policy lock crosses platform I/O or receipt writes. A policy change after admission affects the next independently admitted effect, including the other route of `Both`; it does not revoke an already issued platform call. One owner snapshot covers a group of any size. The product owns authorization, source freshness and condition matching; missing decisions record `not_sent: policy_incomplete`. The product must have committed the original host budget debit, delivery and unknown attempt atomically before enqueueing this worker. The worker never debits that budget again.

`NotificationConfig.deadline` is one end-to-end work budget for a dispatched attempt batch. `run` requires the actual owner's `CancellationToken` and optional absolute parent deadline. It creates one `AttemptContext` before unknown persistence, fresh policy, D-Bus preparation or platform I/O. Both routes, grouped replacements and policy retries share that exact absolute Tokio deadline. Time spent awaiting the pre-effect persistence acknowledgement also consumes the budget. Once an unknown update has been submitted, its custody acknowledgement is still observed after deadline or cancellation as cleanup; the unchanged context is checked before any later work. A shorter parent deadline caps it. The token is a child of the actual owner, so cancelling one attempt cannot cancel its owner or siblings. The context is never serialized or used as authority; the occurrence, budget debit and retry flag stay in the existing checkpoint. The injected civil `DeliveryClock` continues to govern durable quiet holds and is separate from this process-local monotonic work deadline.

Manual `send` and `cancel` callers supply `&AttemptContext`. `cancel` returns `Result<Vec<NotificationReceipt>, PolicyFailure>`; a failed clear authorization leaves the prior checkpoint unchanged and the worker reports the operational failure. Create it once with `AttemptContext::new(configured_duration, parent_deadline, actual_owner_token)` at dispatch and clone it through policy retries. `deadline()`, `cancellation()`, `check()` and `run(future)` expose the same lifetime to non-desktop value/action owners. They likewise create it before durable unknown, authorize under it and pass it to their outlet. An explicit clear/close dispatch gets a new lifetime; it does not reuse an expired Notify lifetime. Owner probes use a separately bounded owner operation, except an import's probe and eligible retry share its one dispatch budget. A later eligible service-appearance retry or quiet-hold wake is a new dispatch of the same checkpoint identity, never a renewal inside the old attempt.

`AttemptContext::run` bounds a cancellation-safe phase and drops that phase on interruption. A SQL owner uses it inside its transaction scope, catches interruption, then explicitly awaits rollback or close before returning. The shared worker does not drop a whole live-transaction callback to enforce its deadline. Cleanup may outlive the work deadline solely to close owned resources; it grants no more execution time. A callback stuck in cleanup is an owner failure to report as stalled. The worker checks the same context before and after the callback and never starts platform I/O on a late positive result. There is no new deadline or token inside the callback, including serialization/deadlock retries. Each permitted retry obtains a fresh complete snapshot under the same original deadline and cancellation; an actual policy epoch change invalidates prior authority.

Interruption before possible Notify or command execution records `not_sent` with `attempt_deadline` or `attempt_cancelled`. Interruption after a possible Notify or successful process spawn leaves `unknown`, which cannot automatically resend after restart. A definitive owner-policy denial records `cancelled`. `PolicyFailure::Unavailable` records `not_sent: policy_unavailable`; `PolicyFailure::Interrupted` preserves the typed deadline or cancellation reason. These operational outcomes never become an inferred denial, timer retry or new hold. Only an explicit `SendDecision::Cancel` inside `Ok(Authorization)` authorizes denial; omitted members do not. Products retain detailed database diagnostics separately from these static receipt reasons. Final receipts still use the durability acknowledgement even after the work deadline; receipt persistence does not authorize another effect. Cancelling the owner while the worker is idle stops it directly.

`SendDecision::HoldUntil { at, policy }` defers the exact ready routes to an absolute millisecond deadline with the owner-computed policy provenance identity. `run` takes an injected `DeliveryClock`; no system clock or local-zone lookup is performed here. The held routes and policy basis survive checkpoint restore. At the deadline, or restart after it, the worker persists an unknown attempt and rechecks current policy. A changed quiet boundary may hold it again. Once that unknown checkpoint has been acknowledged, a crash is terminal rather than a reason to resend. Holds retain the original occurrence, route outcomes and one-retry accounting; they never debit another host budget. `Recheck` wakes this same path after an explicit clock advance or owner update.

Clearing an occurrence schedules any grouped replacement as unknown and persists it before Notify. Manual deliverer users must likewise persist `cancel` before draining `ready_ids` through `send`.

`Import { attempt, imported }` adopts an authenticated, immutable attempt after persisting it. The product validates authority before requesting import. Duplicate original snapshots retain local progress. The worker probes the actual server and persists any eligible D-Bus retry as unknown before sending. Delivered, cancelled and unknown routes are never retried by import.

`Release { delivery_id, released }` stops the source owner. Its update carries the original attempt in `released` alongside the inactive checkpoint. Persist that original handoff in the existing product outbox atomically with the checkpoint before acknowledgement; the source may then forward it to the new owner. Neither operation resets the retry flag or rewrites historical outcomes.

The tests use a private fake notification server and synthetic command routes.
